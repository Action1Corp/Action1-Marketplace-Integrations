# Marketplace And Integration Repository Strategy

## Objective

Separate the Action1 Integration Marketplace host from vendor-specific integrations so integrations can be developed, reviewed, versioned, and released without changing or rebuilding the core Marketplace image.

## Repository Model

Use two repositories:

1. `action1-marketplace`
   - Owns the customer-facing Marketplace application.
   - Owns authentication, setup, roles, deployment behavior, scheduling, logs, framework data tables, package installation, and Marketplace upgrade behavior.
   - Does not ship vendor-specific integration code in the container image.

2. `action1-marketplace-integrations`
   - Owns the integration catalog.
   - Contains one folder per integration.
   - Owns vendor API clients, UI settings schema, handlers, sidebar navigation, React views, and integration-owned database schema.
   - Builds immutable `.tgz` packages and publishes them to GitHub Releases.

## Runtime Model

At runtime, the Marketplace:

1. Reads the integration catalog.
2. Downloads the selected package when an admin installs or updates an integration.
3. Verifies the package SHA-256 hash.
4. Extracts the package into persistent Marketplace storage.
5. Loads the integration backend entrypoint from the installed package.
6. Applies integration migrations.
7. Serves `ui-dist/remote.js` and renders integration-owned React views.
8. Calls integration handlers for validation, manual runs, and scheduled runs.

## Packaging Model

Customer deployments use a Marketplace image with no integration code. Integration releases are separate:

1. Update the integration folder and `manifest.json` version.
2. Run `npm test`.
3. Run `npm run package:all`.
4. Publish package artifacts to a GitHub Release.
5. Publish `catalog/integrations.json` with package URLs and SHA-256 hashes.

The Marketplace can install a new integration package without rebuilding or replacing the Marketplace image.

## Developer Workflow

1. Create a branch in `action1-marketplace-integrations`.
2. Add or update an integration folder.
3. Run `npm test`.
4. Run `npm run package:all`.
5. Open a pull request.
6. Review manifest metadata, UI settings schema, sidebar navigation, React views, migrations, handlers, and generated package shape.
7. Merge after validation passes.
8. Run the package publishing workflow to publish GitHub Release artifacts and update the catalog.

## Integration Package Responsibilities

An integration package should contain:

- `manifest.json` for catalog metadata
- `ui/settingsSchema.json` for integration-owned settings
- `display.json` for Marketplace sidebar navigation
- `ui/index.jsx` and React components for every visible screen
- `ui-dist/remote.js` generated by the package build
- `migrations/*.sql` for integration-owned schema
- `index.js` as the entrypoint
- optional integration-owned validation action and matching handler
- optional integration-owned sync/run action and matching handler
- `README.md` for setup requirements and vendor permissions

## Marketplace Responsibilities

The Marketplace host remains responsible for:

- authentication and authorization
- organization/team management
- setup wizard and deployment configuration
- package download, checksum verification, extraction, and install state
- settings storage APIs and secret masking
- shared Action1 API credential storage
- run history
- schedules
- shared CVE metadata/cache
- applying integration migrations
- invoking integration handlers through the runtime context
